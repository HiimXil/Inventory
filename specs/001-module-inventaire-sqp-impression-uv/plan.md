# Implementation Plan: Module web d'inventaire de stock par dépôt

**Branch**: `001-module-inventaire-sqp-impression-uv` | **Date**: 2026-07-01 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification with 6 user stories, focusing on offline-first counting, ARTIS read-only integration, session lifecycle, synchronization, and RGPD compliance.

## Summary

A web application for stock inventory counting by depot, replacing manual counting. The system operates offline-first on a single device per session, with theoretical stock downloaded at session preparation time (requiring network), then counting proceeds entirely offline via QR scan and manual input. After regaining connectivity, session data synchronizes to the server using last-write-wins per session. Core flows: prepare session (online ARTIS import) → bootstrap snapshot to device → offline counting → sync on network return → closure and Excel export. Built with Next.js 15 App Router, TypeScript, Prisma+PostgreSQL (server), Dexie+IndexedDB (client), Auth.js v5, Zod validation, ExcelJS for export, and Serwist for PWA support.

- Unit: Vitest

**Target Platform**: Web, Chrome/Edge, mobile/tablet-first responsive UI

**Project Type**: Full-stack web application (Next.js monorepo)

**Performance Goals**:

- Session preparation (ARTIS import + bootstrap): < 10 seconds on LTE
- QR scan to visual update: < 200 ms local
- Synchronization trigger to server acknowledgement: < 5 seconds on 4G
- Excel export generation: < 3 seconds for 10k lines

**Constraints**:

- Offline-first: counting continues 100% without network after bootstrap
- ARTIS read-only: no writes to ARTIS ever
- EU data residence: PostgreSQL hosted exclusively in EU, HTTPS enforced
- Single device per session: no multi-device sync
- Session preparation requires network: ARTIS import mandatory, validation strict

**Scale/Scope**:

- ~50 depots, ~200 active sessions/month, ~10k articles per session average
- Mobile/tablet as primary UX (7–12 inch screens)

**Constitution Compliance**:

✅ **I. Offline-First (NON-NEGOTIABLE)**: Counting phase operates entirely offline using IndexedDB cache; bootstrap snapshot downloaded at prep time; no network dependency during counting; sync is single push on network return (last-write-wins). The counting route is served offline by the Serwist-precached app shell (see Decision #6 and research.md R1) — no server auth guard is allowed to block it offline.

✅ **II. ARTIS en lecture seule stricte**: Adaptateur ARTIS server-only, behind stable interface; no direct client calls; no ARTIS IDs exposed to browser; mock ARTIS provided for dev/test (ArtisMockAdapter). Primary implemented import path is `ArtisFileAdapter` (server-side parsing of a client-provided ARTIS `.xlsx` export — read-only, no ARTIS call at all); `ArtisHttpAdapter` (direct calls to the live ARTIS API) remains an optional, unimplemented mode (see Decision #9).

✅ **III. Séparation des surfaces**: Client-side offline island (scan UI on `/sessions/[id]/count`) with IndexedDB; server-side admin, prep, proxy ARTIS, export, auth; boundary is REST API (`/api/sessions/*/bootstrap`, `/sync`, `/export`).

✅ **IV. Sécurité, confidentialité, traçabilité**: 4 roles (Admin, Depot Manager, Logistics, Direction read-only); RBAC guards on all server actions/routes; EU-only hosting; audit events append-only; 24-month retention + auto-purge (FR-025).

✅ **V. Simplicité**: Single PostgreSQL database; no Redis, no WebSocket, no external services; HTTP-only sync; Dexie used for client-side cache only (not as backend store).

**No violations identified. Architecture aligned with all 5 core principles.**

**Structure Decision**: Full monorepo (Next.js 15 with App Router) combining frontend and backend in one deployment unit. The Next.js middleware lives at the repository root (`middleware.ts`) as required by the framework — a middleware placed under `app/` is never loaded. Offline logic isolated in `lib/offline/` with Dexie; server-only code in `app/api/` and `lib/artis/`; client UI in `app/(app)/sessions/[id]/count/` with a `'use client'` directive at the top of `page.tsx`. This minimizes complexity (single DB, no external services) while maintaining clear separation of concerns per constitution principle.

## Technical Decisions & Trade-offs

### 1. Why Dexie, not raw IndexedDB?

Dexie provides a type-safe query API and transaction semantics; raw IndexedDB is verbose and error-prone for multi-table syncing. Dexie schema is declarative.

### 2. Why not WebSocket for sync?

Constitution principle V (Simplicity): single HTTP POST suffices; no real-time bi-directional needed. Last-write-wins is deterministic without ordering guarantees.

### 3. Why Prisma over raw SQL?

Type safety (TypeScript schema + generated types), migrations, and built-in audit-trail support; dev velocity matters given EU hosting constraints (no external tools).

### 4. Confirming sync without re-fetching the snapshot

The `POST /api/sessions/[id]/sync` response returns the canonical server state (session status + reconciled lines). The client relies on that response alone to confirm success and update local status to `SYNCED`. It does **not** re-poll `GET /bootstrap` afterwards — re-fetching the full ~10k-line theoretical snapshot only to confirm a status change is wasteful. `bootstrap` is fetched exactly once, at session preparation, to seed the offline cache.

### 5. Why last-write-wins over vector clocks?

Mono-device session + single push-to-server model = LWW is sufficient; simpler than vector clocks, deterministic, matches offline-first UX expectation.

### 6. Auth enforcement vs the offline counting island

The counting route `/sessions/[id]/count` is an offline island: when the device is offline the request never reaches the server, so neither the middleware nor server-side rendering runs. Authentication must therefore **not** be enforced by a server guard on this route, or the primary flow breaks offline. Resolution (detailed in research.md R1):

- Serwist **precaches the app shell** of the counting route; offline, the service worker serves the cached page rather than a redirect to `/login`.
- Real authentication is enforced **online, at the two server boundaries only**: `GET /bootstrap` (before any data reaches the device) and `POST /sync` (before any data is accepted back). The user is authenticated at bootstrap; offline, the route trusts data already resident on the device.
- The root `middleware.ts` matcher **excludes** `/sessions/[id]/count` (and static/PWA assets) so it produces no redirect that would poison the precached shell.

### 7. Session lifecycle gating (closure requires a successful sync)

Although US5-AC1 allows closing a "locally complete" session from the UX perspective, the server enforces a strict order to avoid a `CLOSED` session with no server-side lines (which would produce an empty export):

**sync succeeds (status → SYNCED) → closure (status → CLOSED) → export.**

`closureSession` rejects any session not in `SYNCED`. `GET /export` requires `status ∈ {SYNCED, CLOSED}`. The UI must guide the user to sync before offering closure, and surface a clear message if closure is attempted on an un-synced session.

### 8. Off-referential lines (`designation` nullable)

A scanned QR whose reference is absent from the imported theoretical stock creates an off-referential line: `theoreticalQty = 0`, `isOffReferential = true`. Since the designation does not exist in ARTIS, the sync payload carries only `{ articleRef, countedQty, isOffReferential }`. `InventoryLine.designation` is therefore **nullable**; the Excel export renders "hors référentiel" in the designation cell for these lines. See data-model.md.

### 9. File-mode ARTIS import as the primary path (`ArtisFileAdapter`)

The primary implemented import path is a client-provided ARTIS `.xlsx` export, not a live call to the ARTIS API (FR-029, FR-033, FR-034):

- `ArtisFileAdapter` parses the uploaded workbook server-side with ExcelJS, matching columns **by header name** (never by index — the real export carries an unnamed, always-blank column), and always reports `pageCount: 1` so the existing page-fetching loop in `lib/artis/aggregate.ts` (built for the network adapter) terminates after one call with no changes needed there.
- `theoreticalQty` is mapped from the **"Stock physique"** column, never **"Qté théorique"** (net of reservations — using it would manufacture false discrepancies on reserved-but-physically-present articles) (FR-033).
- The depot is **selected explicitly by the user** in the prepare UI; the file carries no depot information at all (FR-034).
- The `Depot` table has no ARTIS-side equivalent to discover from: no `listDepots` endpoint exists in the real ARTIS API. Depot rows (the confirmed real codes: `0101`, `0120`, `0130`, `01TR`, and the vehicle depots `01V1`, `01V3`–`01V10`) are seeded by hand in `prisma/seed.ts` and maintained manually going forward.
- `ArtisHttpAdapter` (direct calls to the live ARTIS API) remains an **optional, unimplemented** mode selectable via `ARTIS_MODE=http`; it throws a not-implemented error if selected. It is not required for the current primary flow and is not on the critical path (see task list, Phase 5).

## Risk & Mitigation

| Risk                                                             | Mitigation                                                                                                                                                                                                                                   |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ARTIS import timeout leaves session in PREPARED but unusable     | Timeout guard on server action (10s); explicit error + retry; FR-022. No partial session persisted — session is created only after a fully validated import (FR-021/023).                                                                    |
| Offline app shell stale after PWA update                         | Serwist skipWaiting + clients.claim for immediate activation; app version returned by `/sync` is compared client-side to warn of a shell/schema mismatch.                                                                                    |
| Server auth guard accidentally blocks the offline counting route | Middleware matcher explicitly excludes `/sessions/[id]/count`; E2E offline test asserts the route loads with the network disabled (see Decision #6, research.md R1).                                                                         |
| Closure on an un-synced session → empty export                   | `closureSession` requires `status = SYNCED`; export requires `status ∈ {SYNCED, CLOSED}` (Decision #7).                                                                                                                                      |
| IndexedDB quota pressure                                         | At ~10k lines/session the cache is only a few MB — no near-term risk. If a future depot exceeds ~100k lines, introduce delta-sync/pagination post-bootstrap. Guarded by a StorageManager quota check at bootstrap that warns before caching. |
| RBAC bypass via direct API calls                                 | Guards on every route handler (not just middleware); server actions validate caller role; audit logs all attempts.                                                                                                                           |
| Data retention job fails → RGPD violation                        | Job runs daily in background; alerting on failure; manual cleanup script as fallback.                                                                                                                                                        |
